# Changelog

## Unreleased (SkySpaceAgency)

### From K2-D2 1.4.0 / 1.4.1 (IanMealworm; window fixes by LeoMarinDev)

- **Scenes and campaigns** (K2-D2 1.4.1; not yet flown in game): the pilots are stopped once when the flight scene is left, not on every frame after; **photo mode counts as flight**, so a landing or a burn keeps flying while the player takes a picture (the window hides, then comes back); leaving a campaign closes the window and stops the pilots; nothing of the mod runs in a campaign that has it off (the rails warp watchdog included), except giving back a physics warp one of our burns started. The game's developer console is no longer forced shut every frame. No more "skipped by serialization" warnings at startup.
- **Settings and text fixes** (K2-D2 1.4.0): a slider setting read back from the settings file is kept within its range (before, only the slider clamped it; the installed settings files of 2026-11-19 hold no value out of range), and a field showing an out-of-range value is put back; durations print their tenths of a second (".9", not the milliseconds); **Reset All** (About) also resets both Land profiles' files; "@schlosrat" spelled right in the credits; a missing font reference removed from the console style.
- **Node execution without a lit engine** (K2-D2 1.4.0; not yet flown in game): the Node tab no longer starts a node run with no active engine (lit and not shut down; it says "No active engine - stage or switch one on."), and the API status reads "Node In The Past", "Ready" or "No Active Engine" instead of "Done". During a node burn the burn time counts only the lit engines (it used to count engines still waiting in later stages); with none lit the throttle goes full and the status says so. A start that finds no node flips the Start button back. An engine destroyed in a crash no longer throws in the thrust readings (logged once per vessel).
- **Auto-staging with an empty engine still attached** (K2-D2 1.4.0; not yet flown in game): an engine that was already empty when a stage fired, and stays on the vessel (an SRB with no decoupler under it), is left out of later checks; before, it fired every following stage one after the other, parachutes included. A propellant with no tank capacity no longer stops auto-staging for good (0/0 made the fuel level NaN). The fuel is read only while auto-staging is on. A landing with a chosen stage still suspends auto-staging. Log `[Staging] a lit engine is out of propellant: next stage …`.
- **Pilot guards and Start buttons** (K2-D2 1.4.0; not yet flown in game): Lift, Node and Attitude no longer throw when the game has no SAS telemetry yet (they wait a frame); the Lift, Node and Attitude Start buttons show where the pilot ended up (a refused start flips back to "Start"); Lift **Max Throttle** cannot go under 5 %, and the Node turn tolerances (Turn → max angle, max angular speed) cannot be 0 any more (a turn never finished at exactly 0). The unused `node_ex.show_node_infos` setting is gone.
- **SAS readings looked up once** (K2-D2 1.4.0): the private SAS fields the pilots read several times a frame (telemetry, SAS response, angular delta) are found once at startup instead of on every read; a field missing from the game gives "no reading" instead of an error.
- **Circularize keeps your later nodes; node gizmo on the map** (K2-D2 1.4.0, user decision 2026-11-19; not yet flown in game): the Node tab's Circularize buttons and Lift's circularization remove only the maneuver nodes up to the end of their burn, and keep the ones after it (before, every node went). Log `[Circularize] nodes: removed a up to the end of the burn, kept b after it`. A node created by the mod gets its map gizmo placed once the map is open (it waits up to 2 minutes), instead of failing while the flight view is shown.
- **Lift: "Circularize Once Ascent Complete" works, coasting fixes** (K2-D2 1.4.0; not yet flown in game): with it off (Orbit goal only), the run ends once apoapsis is final, after the Adjust burn, with "Ascent complete - plan your circularization at apoapsis"; before, it was ignored and the run always circularized. **Pause Leaving Atmosphere** now pauses at that point (after Adjust, not when the atmosphere is left), is off by default for a new settings file (a saved value is kept) and is greyed while auto-circularize is on. The transfer and rendezvous goals always circularize: the toggle is hidden for them. Coasting: the edge of the atmosphere is measured from sea level (not from the ground below), the warp is one level lower (it was one too high), no warp while not climbing, and with Coasting Warp off the coast still waits for the edge of the atmosphere (it used to go straight to Adjust). The roll program's SAS lock is released when the ascent ends. The heading correction (Orbit goal) fades in from 5 to 50 m/s of horizontal speed, so the first metres off the pad do not swing the heading. Log `[Lift] ascent complete without auto-circularize (pause on|off)`.
- **Attitude setting names** (K2-D2 1.4.0): the Attitude tab's elevation and heading are saved as `attitude.elevation` and `attitude.heading` (they were `warp.*`). A settings file with only the old names keeps its values (read once; the old names stay in the file).
- **Landing fixes** (K2-D2 1.4.0; not yet flown in game): the Land tab's **Max rotation** slider now limits the turn before the braking burn (it was ignored, 30° was always used; default 10°). A touchdown is noticed even when the height reading is tens of metres off near the ground: in Brake or Touch Down, moving under 1.5 m/s with the thrust at or under half the local gravity for 1.5 s (Kerbin) to about 3.7 s (Mun) ends the landing; never on Minmus-like gravity, never while hovering (log `[Landing] standing still with the engines throttled down`). The vacuum **Precision landing** toggle no longer turns itself off from a high orbit: the note under it says why, and Start refuses with the same message. Stopping a landing releases SAS to hold the current attitude (log `[Landing] stop: SAS target released`). The `[Landing] gear:` lines also give the game's count of parts on the Gear group.
- **Height readings logged** (K2-D2 1.4.0): K2-D2's ground height (0 when landed, never below 0, the vessel's own terrain height low down when the ground reading falls back to sea level, as it does on the pad) is computed next to ours and logged at each landing phase (`[Landing] altitude:`); nothing flies on it yet. Unused vessel helpers K2-D2 removed are gone (no behaviour change).
- **Landing target follows a moved waypoint** (K2-D2 1.4.0; not yet flown in game): after choosing one of your own waypoints in the Land tab's list, moving it in Redux's Waypoints window moves the target with it, as long as you have not set another target since (typed, picked on the map, another entry). Before, the list showed "Custom" at the old place. Mission waypoints, KSC and the picked point do not follow. Log `[Landing] target: waypoint '…' moved from … the target follows`.
- **Window: game UI scale, Redux resize handle, drag fixes** (K2-D2 1.4.1, drag by LeoMarinDev; not yet checked in game): the main window and the VAB tools window follow the game's UI Scale setting. The window is resized with Redux's own handle (bottom-right corner), in width and height, no smaller than 300 x 250; the size is still saved (height in `main_window_size`, width in the new `main_window_width`) and applied when the window is created, within the screen. Moving a window takes the left button only (a right-drag turns the camera without moving it), the window stays inside the real screen at any resolution and UI scale, and a plain click no longer saves its position (it could send the window to the corner on the next launch). A position saved by an older version may land a few pixels off once. Logs `DragManipulator: drag start …`, `WindowSizeSaver: window size saved …`.
- **VAB files from K2-D2 accepted** (preparing the K2-D2 pull request): the VAB tools Import also reads exports whose format is `K2D2.VabExport` (and recognizes a `K2D2.PartsDump`), the names K2-D2 will write; our own files keep `SkySpaceAgency.*`. Internally, every place that names the mod (title, ids, settings file names, logger names, VAB formats) now reads it from one file, `ModIdentity.cs`; the window title and the About title are set from code. Nothing else changes for the player: same settings files and keys, same logger names.
- **Lift: Gravity Turn ascent profile, experimental** (K2-D2 1.4.0 by IanMealworm; Orbit launches only, user decision 2026-11-19; not yet flown in game): a new **Ascent Profile** dropdown under the goal (Orbit goal only) chooses **Guided** (the curve of the 5°/45°/90° altitudes, as before and still the default) or **Gravity Turn (Experimental)**: the rocket rises straight up to the **Kick Speed**, tilts by the **Pitch Kick**, then follows prograde (surface prograde in thick air, orbital prograde in thin air) while the throttle holds a **Hold Time to Apoapsis**, limited by **Max TWR**, **Max Dynamic Pressure** and the target apoapsis, never under **Min Throttle**; the nose comes above prograde when the throttle cannot climb fast enough or a part nears its temperature limit in the air. With **Auto Kick & Hold** (on by default) the kick angle and hold time are chosen just before the kick by flying the ascent ahead for 24 combinations, from the drag measured on the way up and the game's stage data (each also flown with 1.6x the drag); the two sliders are the fallback. The profile is fixed for the run; the Guided settings (rotation altitudes, roll program) and the ascent graph are hidden with Gravity Turn. Prepare transfer and Rendezvous always fly Guided (they need the launch azimuth and plane steering); a Gravity Turn choice is then said next to the status. New settings, K2-D2's names: `lift.ascent_profile`, `lift.gravity_turn_*`. Logs `[GravityTurn] Planning at …`, `Auto plan at …` / `Auto plan not used (…)`, `Predicted path from the plan`, a flight line every 5 s, `Ascent done at …`.
- **Redux's impact prediction, logged next to ours** (K2-D2 1.4.0; logs only, not yet flown in game): during a landing, the point and time where Redux's own impact prediction (the marker it draws on the map) puts the vessel down are logged next to the mod's prediction, with the distance between them, the age of Redux's result and whether Redux calls it approximate (`[Landing] redux impact: …`, when Redux's state changes and every 10 s). Once per landing, the game's own spin vector of the body is logged next to the rotation sign the landing measures (`[Landing] spin: … implied sign … our rotation sign … -> agrees`). Nothing flies on them yet; the reader also checks Redux's prediction settings (assumed attitude, map and flight view) for later use.
- **Redux's stage recovery, logged** (K2-D2 1.4.0; log only, not yet flown in game): at the start of a landing, and when it changes during the landing, the phase of Redux's stage recovery is logged, with the recovered stage's name and capture time when there is one (`[StageRecovery] at landing start: Redux stage recovery Idle`, `… FlyingStage (…) - flying a recovered stage`). Groundwork for the booster return.
- **Landing burn timed with drag for a vessel already falling in the air** (K2-D2 1.4.0; not yet flown in game): on a body with an atmosphere, a regular propulsive landing started (or re-coasting after a brake) inside the air used to time its burn as if there were no air: it lit the engines kilometres too high, braked to a stop, fell and braked again. While the vessel coasts down, its drag is now measured from how it actually slows, and the burn starts at the last moment whose braking still ends 50 m above the ground (the airless start stands in until a drag is measured, always earlier). The braking then re-solves its throttle several times a second to end at 50 m, tilting at most 15° off vertical to kill the sideways speed, and hands over to Touch Down's final descent there (legs, contact speed and touchdown detection unchanged). The descent from orbit (its atmospheric coast already predicts the brake with drag), airless bodies, the parachute modes, precision landings and a landing with a chosen stage are unchanged. Logs `[Landing] air timing: in … brake in … s (vacuum start in … s)`, `[Landing] air timing: brake at …`, `[LandingBurn] braking at …` every 2 s, `[LandingBurn] handover to Touch Down at …`.

### Changed

- **Native rails warp during burns, now the default** (every closed-loop burn: Transfer, Orbit, Circularize, Node, Lift, Rendezvous away from the target; 2026-11-15, for Redux 26w46a; not yet flown in game). Redux 26w46a fixed the game's rails warp under thrust: the burn now follows the lit engines, is rebuilt when their thrust or direction changes, and stops when they stop (read in the game's code on 2026-11-15; players confirm native nodes warp correctly). Before, it was a fixed burn to the stage's burnout, which burned ~500 m/s per injection in our 2026-10-24 test.
  - **Node tab → ADVANCED → "Warp during burns"**: Off (1x) / Physics (x4) / **Rails (native)**, the new default. A settings file without the key, or with the old "Physics + rails" value, reads as Rails; a saved Off or Physics is kept.
  - **How a Rails burn flies**: alignment and ignition at 1x; after 1 s aligned within 1° at full throttle, the game's rails warp at the highest of x100, x50 or x10 that still leaves 8 s of real time before the exit; the game steers nothing on rails, the burn keeps its direction. Near the end the warp steps down one level at a time, then drops to 1x 15 s of burn (or 10 s of stage) before the end, plus 2 s of real time at the rate, and the closed loop finishes the burn on the target orbit. One rails stretch per burn.
  - **Guards**: if the game does not take the burn within 3 frames, stops flying it, or the trajectory does not speed up (under half the modelled acceleration after 3 s and 10 frames), the burn drops to 1x at once and finishes without warp (log "rails burn: the game does not take the burn …"). Leaving the atmosphere's or the surface envelope's margin, the aim drifting 5° from the burn direction, or a rendezvous target within 2 km also end the stretch.
  - **Removed**: the 2-minute minimum burn, the physics-warp stretches around the rails stretch, and the check of the game's private burn patches (`_numBurnPatches`, read by reflection). The physics warp stays available as its own mode.
  - **Never on rails while burning**: every landing burn (deorbit, braking, final descent, precision and reentry phases), the heat guard, anything in an atmosphere or under the surface envelope, and rendezvous burns within 2 km of the target and docking. They stay at 1x (or physics x4 in the Physics mode).
  - **Warp watchdog**: it now drops only a rails burn nobody commands (throttle at 0, an engine still giving force when the warp started). A burn the player flies by hand under rails warp (a native node) is left to the game. The rule "throttle 0 and no engine force for 1 s before a coast rails warp" stays: in 26w46a the game still starts a burn from a leftover engine force.
  - Transfer log: the energy accounting of the previous burn ends at the next ignition, so the physics switches of a rails stretch are not reported as a burn nobody commanded.

### Fixed

- **Lift "Rendezvous" messages and warp** (follow-ups of 4.4; 2026-11-18, not yet flown in game): a refusal on the pad no longer advises "press Start again" (it says nothing was launched); a stop caused by leaving the flight scene, a vessel change or the mod being off in the campaign says so, instead of "Stop pressed, or another pilot started"; the first plan of the launch passes now sets the warp to 1×, like the re-plans. A target around another body points to the Rendezvous tab's new button.
- **Land tab: the game's heat settings are taken into account** (2026-11-18, at a player's request; not yet flown in game). A campaign played with heat turned off could still be refused a landing ("Reentry too hot for the engines …"), pay a pre-brake, or have the heat guard burn its Δv, for a heat the game does not apply. The landing now reads the campaign's difficulty, through the same calls the game's thermal systems make (read in the game's code, Redux 26w42c and 26w46a):
  - **Heat off** (difficulty "HeatEnabled" off, or the "Disable Thermodynamics" cheat): the game heats nothing. The descent is planned on Δv alone (cheapest entry, no pre-brake, no heat refusal), no part is heat-predicted, the heat guard stays off. Log `[Landing] heat: game heat disabled, …`.
  - **No part destruction by heat** ("HeatPartDestruction" off): the game lets parts pass their max temperature without destroying them, and an engine keeps working hot. The heating is still predicted and logged, but never refuses nor costs a pre-brake, and the heat guard stays off; above 100 % of an engine's max temperature, the start shows a warning only. Log `[Landing] heat: game part destruction by heat off, …`.
  - **Heat scaling** ("HeatScaling"): applied to the predicted flux as the game applies it (it multiplies the whole flux source); 0 is now kept as 0 (it was ignored and read as 1).
  - An option that cannot be read keeps the previous behaviour, and the log line says which one (`… not read: taken as on`).
  - The plan's 70 % limit, the guard's 75 % and the 90 % alarm are unchanged when heat is on (confirmed by the user on 2026-11-18).
- **Transfer tab: returns from a moon whose orbit is inclined or turned (Minmus, Ike, …)** (2026-11-18, after the in-game Minmus → Kerbin try on Redux 26w46a; not yet flown again). The plan aimed at a 100 km Kerbin periapsis, the injection was flown to its asymptote within 0.2 m/s, and the vessel left Minmus for a 37 831 km periapsis on a path out of Kerbin's SOI. The game gives the vectors of an orbit in the celestial frame of its body, turned within its parent's by the body's CelestialTilt (its orbit's inclination, node and periapsis argument, then its axial tilt; read in the game's code). Kerbin's and the Mun's frames are not turned, which is why the Kerbin and Mun transfers never showed it; Minmus's is (about 116° for stock Minmus), and the transfer code summed Minmus's vectors as if they were Kerbin's.
  - Every vector the transfer code reads (the bodies' orbits, the vessel) is now turned into the star's frame, and every burn's guidance turned back into the frame the burn reads the vessel in. Inclinations (arrival, capture, final orbit) are measured in the body's own frame, as the game's. Lift "Prepare transfer" keeps the launch in the launch body's frame and turns the planned parking plane into it.
  - Log: each `[Transfer] body …` line gives `frame turned …° from the root's`; the frame check at the start adds `tilted chain vs world … m` (a few metres expected) next to the old `chain vs world`.
- **Transfer: a child → parent return that ends up in the parent's SOI no longer stalls** (2026-11-18, same flight):
  - **SOI change**: no more "state mismatch after the burn: about 17.23 m/s nobody commanded" when the vessel changes body: the energy accounting restarts around the new body (log "the central body changed (Minmus -> Kerbin), accounting restarted …").
  - **SOI exit**: a vessel still a few metres inside our SOI radius of the moon it just left, moving away, is no longer taken for an entry still to come ("late SOI entry into Minmus: Missed", then "failure in Escape … the Minmus encounter passed outside its SOI"). Log: "inside our SOI radius of Minmus but moving away from it: an exit the game has made".
  - **Correction in the target's SOI with no periapsis ahead** (an open path that leaves the SOI): no more 300 m/s solve aiming at a periapsis already passed ("arrival UT …" before now). The rest of the plan becomes the orbit at the target, as the Orbit tab plans it: a capture (at the periapsis when it is ahead, otherwise as soon as possible), then the requested orbit. Log: "correction n: in the Kerbin SOI past its periapsis …: the rest is planned as an orbit at Kerbin".
  - **Resume and new transfers** in the target's SOI: "The target is the body you are orbiting." is gone. A search from the target's SOI (Resume after a failed correction, the "new transfer" offer, or Kerbin picked while around Kerbin) plans the orbit at the target (case "In the target's SOI"); a vessel already on the requested orbit gets "Already in the requested orbit around Kerbin.".

- **Land tab: the reentry heating judges the engines only** (2026-11-04, after the first in-game try; not yet flown again). Brake from a Kerbin orbit was refused with "Reentry too hot: even braking 3164 m/s before the atmosphere, storage_0v_battery_electricity_radial reaches 193 % of its max temperature". The model gives every part the full airflow on its own face (the game's shock-cone shading is not modelled), so a light radial part (a battery: almost no thermal mass for its area) came out far too hot, and the 3164 m/s was only the largest pre-brake tried (95 % of the air speed at the interface), not a need.
  - The planned check (70 %), the heat guard (75 %, alarm at 90 %) and the "Hottest Engine" row (was "Hottest Part") now look at the parts carrying an engine module only: they lead at retrograde, and losing them ends the landing.
  - The other parts are still heated and logged ("hottest other part (not judged)"), never refused on. Without any engine among the parts read, the check passes with a note.
  - New refusal text: "Reentry too hot for the engines: even braking … m/s before the atmosphere, the engine … reaches … % of its max temperature (limit 70 %)." When the largest pre-brake fails for another reason (the brake after it, or the prediction), the message now says that instead of quoting a temperature.
- **Lift "Prepare transfer" now warps while waiting on the pad** (2026-11-04). The clock stayed at 1x for the whole wait ("Launch in T-1h 21m"): the vessel sat at full throttle on the pad, and the rails-warp gate waits for throttle 0 ("[Warp] waiting for the engines to stop before rails warp (throttle 1, 0 force(s))"). The pad wait now holds the throttle at 0 until T-0 (log "[Lift] pad wait: throttle … cut to 0"), warps to 30 s before the launch, then launches at full throttle as before.
- **Transfer targets: the star is no longer offered** (Lift and Transfer tabs, 2026-11-04). The Lift tab could plan "a transfer to Kerbol from Kerbin" (33360 m/s). The target lists leave the star out, and a saved star target is refused: "Kerbol is the star: choose a planet or a moon."

### Added

- **Transfer tab: gravity assists** (sub-project 4.6; not yet flown in game). With "Use gravity assist" ticked, the search also looks for plans with one flyby, of a planet on the way (Eve on the way to Moho, or Kerbin itself) or of a moon on the way out (the Mun, leaving Kerbin). The search covers the departure date, the flyby date and the arrival date. A flyby passes at least 10 km above the atmosphere or the terrain. When the turn needs it, it is powered at the periapsis, and that burn counts in the total. An assist is offered only when it saves at least 5 % of the direct plan's Δv and fits the maximum trip. The tab then shows both plans, for example "Direct: 5 070 m/s, 137d" and "Via Eve: 4 272 m/s, 313d". The cheaper one is preselected, and a click chooses the other. In flight, the corrections before the flyby aim at its periapsis and plane, and the ones after it aim at the target; a flyby burn is flown at 1×. Resume keeps the assist when it still can, and otherwise says so and plans without it. Transfer + rendezvous (Rendezvous tab) uses the assist when the option is ticked, and takes the cheaper plan. The search runs in the background, for 30 s at most (about 1 to 2 s in the editor for Kerbin → Moho).
  - On the stock-like test system, no single Eve flyby pays on the way to Jool (at best 2 % saved, so it is not offered); Kerbin → Moho via Eve saves 16 to 18 %, and a Mun flyby on the way to Duna about 3 % (not offered).
  - Log lines: `[Transfer] assist: direct …`, `grid via …`, `built via …`, `departure via …`, `offer: …`, `resume …`, and in flight `leg … starts in <body>: flyby …`, `flyby of <body>: periapsis predicted …`, `flyby of <body> done: excess out …`, `resume of an assist via …: route …`.
  - With the option unticked (the default), the search, the plan, the flight and the plan file are those of before.

- **Rendezvous tab: "Transfer + rendezvous + dock" and "Transfer + rendezvous" for a target around another body** (sub-project 4.5; 2026-11-18, not yet flown in game). One press plans a transfer into a circular orbit 10 km under the target's periapsis (at least the low orbit, at most the low orbit + 150 km), in the plane closest to the target's that the arrival allows: the arrival corrections aim the plane, no separate burn. The rest of the plane is flown by the Rendezvous pilot's plane match, and budgeted. The rendezvous itself is planned at the arrival, from the target's actual phase; the plan budgets the worst of 12 phases, plus 10 m/s for the docking. The tab's plan table shows every transfer step, the plane match left, the rendezvous and the docking, and the total; the start is refused, with the numbers per stage, when the vessel cannot pay for it. Then the mod flies the transfer (or makes its nodes with Prepare only), and in the parking orbit hands over to the Rendezvous pilot: rendezvous, then docking (the second button stops after the rendezvous). A stop says which step and what is left; Resume, in the Rendezvous or the Transfer tab, plans the transfer again from where the vessel is, and the rendezvous still follows. If the target disappears during the transfer, the vessel still reaches the parking orbit and the hand-over stops with the reason.
  - The target's plane is read again at each arrival correction (a change above 0.01° is taken and logged). A target landed, around the star, on an open orbit, with its periapsis in the atmosphere or under the terrain, or around our own body (4.3's buttons) is refused before any burn.
  - Planning takes about 10 s in the editor (the transfer search, then 12 rendezvous plans), on a worker thread with a progress bar. In a typical Kerbin → Duna geometry, a station inclined 30° leaves about 33° of plane after the arrival (the arrival's plane must contain the incoming asymptote): a plane match of several hundred m/s, budgeted and shown.
  - Log: lines `[Transfer] chain:` (plan, asymptote, estimate, total, the plane at each correction, the hand-over); each correction line adds `plane error predicted …°`.
  - The rendezvous counts in the stage check until the departure. After it, a correction that eats into the rendezvous margin no longer stops the transfer on a flyby: it goes on to the parking orbit, and the Rendezvous pilot checks its own budget there. A resume inside the target body's SOI (after a failed capture) plans the orbit there in the target's plane, then hands over; a resume whose target is gone no longer aims at its plane nor budgets its rendezvous.
- **Lift tab: goal "Rendezvous with [vessel]"** (sub-project 4.4; 2026-11-18, not yet flown in game). On the pad, the mod scores the next launch passes (up to 12 within 4 turns of the body) by the rendezvous each would leave after the ascent, and launches on the cheapest (within 5 m/s, the earliest). It lifts into a circular orbit 10 km under the target's periapsis (at least the low orbit, at most the low orbit + 150 km: the Rendezvous pilot's phasing raises the rest), then hands over to the Rendezvous pilot: rendezvous, then docking when "Dock after the rendezvous" is on. There is no Lift plane trim for this goal: the Rendezvous pilot's plane match flies any plane left.
  - A target plane the site cannot reach is shown with its plane change, flown by the Rendezvous pilot's plane match. For a nearly equatorial target (launching at any time costs at most 5 m/s more), the passes sample the target's orbit instead of one pass per turn of the body.
  - The first pass is at least a minute after Start (the plan takes a few seconds of game time). A missed launch time plans every pass again (the first stage is never fired twice).
  - A target that is landed, around another body, on an open orbit or with its periapsis in the atmosphere is refused before anything is launched; a target gone or landed at the hand-over stops the chain without starting the Rendezvous pilot.
  - A stop says which step failed and what is left; the Rendezvous tab then has the target pre-selected. The player's Ap setting is not used for this goal and never changed.
  - Log lines `[Lift] rendezvous:` (planning, one per pass, chosen pass, orbit at the hand-over against the prediction, hand-over started or refused).

- **Land tab: Brake deorbits by itself, refuses what it cannot pay, and guards the reentry heating** (Propulsive mode; 2026-10-30, not yet flown in game). Pressing Brake in orbit did nothing ("None detected"): it now plans the whole descent before anything moves.
  - **Deorbit**: a closed-loop retrograde burn, planned again from the orbit reached. Airless body: periapsis 2 km under the datum, as the precision landing (a shallow descent, the cheapest powered one). Atmospheric body: an entry periapsis among 60 % to 0 % of the atmosphere depth, the one with the lowest total Δv whose predicted heating stays under 70 % of the parts' max temperature. Then the usual Pause → … → Touch Down on an airless body.
  - **Atmospheric body**: when needed, a retrograde pre-brake ending 15 s before the atmosphere, then an atmospheric coast: warp up to a minute before the interface, 1x in the air, surface retrograde, and Brake at the start predicted with drag (not from the vacuum orbit any more, which braked from orbital speed). Also used when Brake is pressed above the atmosphere on a collision course.
  - **Δv refusal**: deorbit + pre-brake + brake (+10 %) against the vessel's Δv, refused with the numbers: "Δv 850 m/s for ~1122 m/s needed (deorbit 120, pre-brake 400, brake 500, +10 %)." The brake is simulated on the trajectory after the burns (with drag on an atmospheric body). An entry too hot even after the largest pre-brake is refused with the part and its predicted temperature.
  - **Heating model** from the game's own (read in the IL): reentry flux 500 · (v/300)³ · area · ρ^0.53 · Cd^0.3 · harshness above Mach 1, each part's temperature integrated with its thermal mass, air exchange and radiation; the 12 parts most at risk, at retrograde. Judged up to the planned brake start.
  - **Heat guard**: from 75 % of a part's max temperature, above Mach 1, it thrusts surface retrograde (25 % to full throttle at 85 %) until the part is back under 70 %, in the coasting modes; it aims never to pass 90 % and says so when it cannot ("Overheating: …"), or when it eats into the brake's Δv. A "Hottest Part" row shows the live temperature.
  - **Landing with a chosen stage** now starts from orbit on an airless body (stage 1 pays the deorbit with 10 % to spare, the landing stage its brake with 20 %). On an atmospheric body it still needs a collision course inside the air: the staged plan has no drag model.
  - **Precision landing** on an atmospheric body in Propulsive mode gets the same deorbit, heating and Δv check, without target.
  - Log: "[Landing] deorbit: …" and "[Landing] heat: …".

- **Orbit tab: capture from a flyby** (2026-10-30, not yet flown in game). Inside a body's SOI on an open trajectory (hyperbolic, or elliptic with its apoapsis beyond the SOI), the tab no longer refuses with "No closed orbit to plan from". The first step is a capture burn, then the usual plan, each step planned again from the orbit actually reached (one node at a time, flown by the closed-loop burn):
  - **Where**: at the periapsis when it is ahead, above the surface and atmosphere and at least 60 s away; otherwise as soon as possible (60 s from now, the lead of the other burns), for example past the periapsis on the way out.
  - **Into what**: an orbit in the trajectory's plane through the capture point, with the ticked Ap / Pe; an unticked one stands at the capture radius, so with nothing ticked the capture is circular there. - **Land with a chosen stage** (Land tab, powered braking; 2026-10-25, not yet flown in game). A new "Land with stage" list shows the vessel's stages in the staging stack's order, counted from the active one (stage 1). The default, the current stage, lands exactly as before. With a higher stage, the lower stages brake first, the way a Duna booster with 755 m/s left can now pay for part of the braking instead of being thrown away:
  - **Drops**: the active lower stage is dropped when it runs dry (no thrust for 0.5 s) or at the drop height at the latest, one activation at a time, never while paused, after leaving rails warp, and checked: the dropped parts must leave within 3 s. Then the next one, until the chosen stage is active; it lands as before (legs, final descent).
  - **Safe at the drop**:
    - The throttle is cut to 0 before every activation and held through the separation, so a booster with fuel left cannot brake harder than the lander and be hit by it.
    - The new stage must push within 1.5 s; otherwise one more activation is fired if it drops or fires nothing that matters, else the landing stops with a message.
    - Auto-staging is suspended during a staged landing, and the drops are counted from the game's staging.
    - A plan that stops working mid-run shows an error in the status line. The pilot then drops the lower stage at once if the landing stage alone can still finish, or brakes now if it is still waiting.
    - A staged start needs a collision course, so that the drops can be planned.
  - **Drop height**: the highest of 2 km above the ground, the lowest height from which the chosen stage alone, braking at once, still stops at the hand-over height with 20 % Δv to spare, and the new ADVANCED setting "Drop lower stage at the latest at (km)" (empty = automatic; it never lowers the safe height).
  - **Start checks**: the braking simulation models the drops (mass, thrust, Isp and Δv of each stage, a 1 s gap per drop). A plan that does not work is refused with numbers ("Stage 2 alone cannot brake from 1240 m/s: it has 980 m/s."). A stage whose drop would take the landing legs, a parachute, a docking port or the command part is never dropped, and the start says so.
  - **Log**: "[Landing] stage plan: …", "[Landing] stage drop …" with the reason and the altitude against the plan, and "[Landing] staged braking: predicted … | actual …" at touchdown.
  - **Precision landing** (vacuum) works with a chosen stage too: the stop-point prediction, the deorbit search, the corrections and the Δv budget use the staged vehicle and the same safe drop height search as the plain landing, which the flight then keeps (at least 500 m above the hand-over, so the terminal guidance flies on the landing stage). The start refuses when the active stage cannot pay the burns before the braking with 10 % to spare (it is never dropped during them) or when the landing stage lacks 20 % margin over its part of the braking and the terminal reserves.
  - Parachute mode is unchanged.

- **Align before warping to a burn** (every closed-loop burn: Transfer, Rendezvous, Lift, Node, Orbit, Land; 2026-10-25). It gives up after 60 s, or twice the alignment lead if longer, with a message. Log: "pre-aligned: … off, rate …", "warping to the burn at UT …".

- **Transfer pilot**, behind the Transfer tab: the tab's Plan, Start, Stop, Resume and Cancel buttons drive it.

  - **Flight**: warp to the window, then each step of the plan: orbit or plane change, injection toward the departure asymptote, SOI exit, three corrections solved in flight toward the arrival periapsis, and the capture at the periapsis. The warp stops before every burn and every SOI change. A correction under 1 m/s is skipped only when the path already meets the wanted periapsis within 1 km. When a correction picks another arrival pass, the capture and the later steps move with it.

  - **Prepare only**: one game node at a time for the next step, no warp; the next step is planned from the orbit reached once the player has flown the node (node removed, or at least 80 % of its Δv flown with the engines off for 5 s). Only the mod's own node is removed.
  - **Resume**: the plan is saved per vessel in `mods/SkySpaceAgency/plans/` at every phase change. When that vessel is next active in flight, the mod offers "Resume plan to {body} (next: {step} in {time})", and never flies a saved burn again: every burn still ahead is planned again from the actual state.

### Changed

- **Long burns speed up with the game's own burn prediction** (rails warp x10 or x50, 2026-10-25; not yet flown in game): transfer, rendezvous, Lift circularization, Node tab and Orbit tab burns. Landing and reentry burns keep physics warp, x4 at most.
  - With more than 2 minutes of burn left, aligned within 1° at full throttle for 1 s, the mod hands the middle of the burn to the game's rails warp, which flies a burn it computes once (fixed direction, the active stage's flow). It picks x50, or x10 when x50 is refused or too short, so that the stretch lasts at least 15 s of real time. With auto-warp off, no rails warp.
  - It does so only when the ideal direction stays within 5° of that fixed one until the end of the stretch, outside the atmosphere and above the game's surface envelope and more than 2 km from a rendezvous target.
  - The mod checks that the game's burn really runs: at once if the game switched without a burn, within 2 frames otherwise. If not, it drops back to physics warp at once and does not try rails again for that burn. If the game's "no time warp under thrust" setting refuses rails, the log says so.
  - It leaves rails while 15 s of burn and 10 s of the stage's fuel are still left, plus 2 s of real time at the warp rate actually applied (a frame hitch cannot run past them), and steps down from x50 to x10 about 5 s of real time before. The time left is computed with the lower of the modelled and the measured acceleration. The end of the burn and any staging are flown in physics warp, closed loop. One rails stretch per burn.
  - The log shows each step (`rails burn:` lines): entry and rate, the check, the reason for leaving, and the Δv applied on rails, planned against actual.
- **Closed-loop burns run under physics time warp, x4 at most** (2026-10-25; not yet flown in game): transfer, rendezvous, Lift circularization, Node tab, Orbit tab and the landing deorbit and correction burns.
  - The mod switches the game's physics warp mode on at 1x, then raises the warp to x2 or x4. The vessel keeps its real physics, so steering and throttle keep working. Rails warp is never used while the engines push (since then, see the rails stretch of long burns above).
  - The warp follows the existing limits (5 % of the remaining Δv per frame, at least 10 s of real time left, 1x when not aligned), with x2 at most in the last 30 s of the burn. With auto-warp off, the mod only lowers the player's warp.
  - Rails warp during a burn, physics mode lost or a vessel leaving real physics drops the warp to 1x at once. When the burn ends, stops or fails, the warp goes back to 1x and the warp mode the player had before is restored.
  - The landing descent itself stays at 1x.
- **Throttle cut on our vessel after a vessel switch** (Transfer and Rendezvous pilots, 2026-10-25). Stopping or failing now sets the throttle (and the RCS translation) to 0 on our own vessel even when another vessel is active: the game keeps the throttle of a vessel the player switches away from, so its engine would keep firing.
- **Transfer and rendezvous search** (2026-10-24): the search no longer considers a wrong solution. The orbit solver behind it could report, between two points of nearly the same orbit with several revolutions, an orbit that missed the aim by up to 700 km; it now finds those orbits precisely or reports none.
- **Precision landing rewritten for bodies without atmosphere** (precision landing part 2, 2026-10-21; not yet flown in game).
  - Goal: stop within 100 m of the target for at most 20 % more Δv than a landing without target; over 20 % the landing is refused at start with the numbers.
  - The planner predicts the real stop point (braking and body rotation included, the longitude and rotation directions measured in game), searches the deorbit time, plans a plane change itself when the target is not under the orbit, solves a mid-course correction, brakes to a stop at the Touch Down altitude, then a terminal guidance brings the vessel down above the target. Δv per phase, predicted and final distances are shown in the Land tab.
  - Refuses a starting orbit that is too low for the terrain under it (raise it with the Orbit tab) or whose periapsis is above 100 km.
  - Once the vessel is on an impact course, a precision failure never turns the pilot off: the correction is skipped, or the pilot lands without target.
  - The old empirical rotation factor (×1.307) and the 36-sample deorbit scan are gone, with their Extend/Shorten/RCS fine-correction settings.

- **Precision landing safety** (2026-10-21, airless bodies).

  - The plane-change burn is planned at least 130 s ahead (was 60 s), so the vessel has time to turn before it.
  - The precision brake goes to full throttle as soon as the simulation says it would stop below the hand-over height (before: only below 50 m).
  - The "Braking ends below the hand-over height" warning is also shown when the deorbit is re-planned; the last "Landed … m from the target" message is cleared when any landing starts.

- **Landing autopilot safety**:
  - **Refused starts**: Start (Brake or Touch Down) now refuses to start, with a message that stays in the tab, when:
    - no engine is active;
    - the local TWR is too low to stop safely (the plan counts on 85 % of the thrust);
    - even braking now would hit the ground;
    - the vessel has less than 110 % of the Δv the braking burn needs.

    When the game reports no Δv, the tab shows a warning instead of refusing.
  - **Braking start**: braking starts at the latest moment that still stops 50 m above the terrain. A simulation of the burn finds that moment, accounting for gravity, the approach angle, mass loss, body rotation and the terrain under the path. "Burn before" is now an extra margin on top.
  - **Descent speed**: the speed limit in Brake (precision) and Touch Down is now capped by what the active engines can stop. The altitude/speed profile still applies when it is slower.
  - **Engines**: only active engines (ignited, not shut down) count for landing. With no thrust the throttle goes to 0 instead of NaN.
  - **"Cannot stop before the ground!" alert**: shown when stopping is no longer possible: in Brake, according to the simulation; in Touch Down, when even full thrust is not enough. Touch Down then brakes at full throttle.
  - **Brake (non-precision)**: now ends on total surface speed instead of vertical speed. Before, a shallow approach could leave Brake before it burned at all.
  - **Failed phases**: a Circularize or deorbit phase that cannot do its job now stops the landing and shows why, instead of moving on to the next phase.
- **Orbit prediction on very eccentric orbits**: the two-body propagator used by the landing, Orbit and Node predictions could, in rare cases near periapsis, fail to converge and return a position far off (1.6e9 m in the case found). It now falls back to a bracketed solve; every case that converged before gives the same result.
- **Orbit prediction on long hyperbolic steps**: the same propagator could return a wrong or NaN position on an escape or arrival hyperbola predicted far ahead (for example 1e7 s after leaving low Kerbin orbit). It now starts from a hyperbolic guess and its fallback survives the overflow far out. Closed orbits that converged before give the same result.

## 1.3.0

### Added

- Node autopilot: two new buttons to create a maneuver node at the next apoapsis or at the next periapsis.
- Ascent autopilot can now create and fly its own circularization node at the end of ascent, instead of requiring one to be built by hand.
- Ascent autopilot can fly a specified roll program during the climb.
- Landing autopilot can now perform precision landings on bodies with no atmosphere, targeting a specific site via Redux's own waypoint system. (An atmospheric version of precision landing exists in code but is still a work in progress and not yet exposed to players.)

### Changed

- Every autopilot now deletes the maneuver node it executes once the burn finishes, instead of leaving it sitting on the plan.
- Precision landing settings for bodies with and without an atmosphere are now two fully separate autopilot profiles, so tuning one can't affect the other. (The atmospheric profile is still work in progress and not player-facing yet.)
- Node's "Rotate During Burn" option (Node tab, Experimental section) now defaults to on, so SAS stays locked to the maneuver direction for the whole burn instead of dropping to Stability Assist partway through. Since every burn in the mod shares the same execution code, this improves accuracy for Node, Lift's circularize, and Landing's burns, not just Node's own. The toggle is still there for anyone who wants the old fixed-orientation behavior back.
- All custom UI controls migrated from the legacy `UxmlFactory`/`UxmlTraits` pattern to the modern `UxmlElement` attribute system.
